find github issues and pull requests by asking

someone may have solved that bug before you lost the morning to it. a bot searches github issues and pull requests by repository, author, label or status.

by the Metal team · checked 12 november 2026 · how we made this

it brings back matches and the search words it used. start in the repository where the error happens, then read the closest report for symptoms and affected versions.

search issues and pull requests, in plain words

find the earlier investigation before starting yours from scratch. describe the error and name the repository. the bot combines words with filters for people, labels and open or closed work. say whether you want issues, pull requests or both.

it can sort matches and fetch more results. have it open the promising reports: a closed issue helps only if the fix covers your version.

a routine to copy

paste this into a chat with your bot

every tuesday at 9, search larchstone-dev/atlas for open issues and pull requests mentioning "export timeout".

- show the search words and repository
- group matches into issues and pull requests
- read promising matches before calling them the same problem
- say if unread results or search limits leave gaps

return the report here. never label, close, assign or comment on anything.
when
tuesdays at 9:00
needs
github connected with read only; allow search and reading matched issues or pull requests

what comes back looks like this (an example)

larchstone-dev/atlas
search: repo:larchstone-dev/atlas state:open "export timeout"
issue #47: large exports time out.
pull request #52: retry change; needs a closer read.
no repository changes.

good jobs for it

  • avoid a duplicate report. look for closed issues about the same error first.
  • see what might fix it next. find open pull requests that mention your component.
  • cover a teammate. find their assigned issues before they leave for holiday.

before it runs

Metal counts Search issues and pull requests as a read: it looks and changes nothing. a bot you allow only to read can use it.

how to start

  1. keep it read only. connect github for this search bot.
  2. name the search area. give the owner, repository and error phrase. choose issues, pull requests or both.
  3. inspect a match. ask for the search wording and any gaps beside the results.
  4. keep the investigation on your radar. schedule the search, then change the question as the problem narrows.

limits worth knowing

  • private work needs access. a repository your account cannot open will not appear.
  • finish the search before ruling out an earlier report. accessible repositories can still hit github search limits. ask the bot to show any gaps.
  • find out whether the fix reached your version. open the closed issue and read the affected versions.

try it in 2 minutes

  1. connect github with read only
  2. name one repository and an error phrase
  3. ask for issues and pull requests separately
  4. open the closest report and compare the symptoms

ask for the search words with the results. it is the quickest way to spot the wrong scope.

mistakes people make

searching every repository at once

start where the error happens. widen the search if that finds nothing.

calling a similar title a duplicate

read the symptoms and affected version before joining the reports.

before calling it a duplicate

  • same symptoms, not just the same title
  • same component and relevant version
  • the bot read the report, not just the search result
  • any access or search gaps appear in the answer

questions

can it search only pull requests?

yes, say pull requests only. have it show the exact search wording beside the matches.

does no result mean nobody reported it?

try a different error phrase before giving up. wording, repository access and search limits can hide an earlier report. have the bot name any gaps.
