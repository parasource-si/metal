a github bot that reads the work before you weigh in

walk into standup knowing why the pull request stalled. connect github to a Metal bot for issue context, changed files and release outlines.

by the Metal team · checked 12 november 2026 · how we made this

choose claude, chatgpt or another ai. a read-only bot brings the findings here. add labels, assignments or comments later, once you want it to act on the queue as well as read it.

what a bot can do in GitHub

find the workaround before asking someone to debug it again. search earlier reports, read the issue and see what reviewers already said. these actions give the bot the context for a useful answer.

actionMetal treats it aswhat you would use it for
Search issues and pull requestsreadlook for earlier reports of the same error before calling a bug new
Get an issuereadread the reproduction steps and the original report
Get issue commentsreadfind the workaround someone already left in the comments
List pull requests filesreadsee which files a proposed change touches
List reviews for a pull requestreadread reviewer feedback before summarising what is blocked
List commitsreadgather commit messages for a release briefing
Add labels to an issuechangeapply a triage label after you have agreed the rules
Create an issue commentsend: asks firstpost a requested follow-up through the sending approval setting

composio, the connection service behind Metal's apps, lists 905 GitHub actions (version 20261104_00, read 12 november 20265). Metal treats 474 as reads, 13 as sends and 418 as changes.

only actions starting with a read word (get, list, search) count as reads, so a read-only bot can't call the rest. a send reaches people or moves money, like add email for auth user, and waits for your Allow unless you set a daily amount.

connect GitHub

  1. open Connected apps in the sidebar.
  2. pick GitHub and sign in on GitHub's own page, so your password goes to them and never to a bot.
  3. choose which bots may use it, and whether each may only read or may also change things. your bookkeeper doesn't need your GitHub.
  4. ask in plain words. reading and drafting happen freely; sending asks you first.

start with the repo you need for tomorrow's standup. open connected apps, connect github and give your review bot read-only access. sign in on github's page, then name the exact owner and repository.

the catalog lists what github can do. your bot can use only the actions you allow.

routines to copy

get the duplicate report, stalled review or release outline before the meeting. pick one repo and one question. these routines return findings here. read the first few results before allowing writes.

spot a duplicate report

when an issue opens in amberquay/widget, read it and search earlier reports for the same error. tell me possible duplicates and missing reproduction details here. say when the evidence is thin. never label, assign, close or comment.

when a github issue opens · possible duplicates and missing details, with issue references

find who a review needs next

every tuesday at 10, read open pull requests and reviews in amberquay/widget. group them by waiting for author, waiting for reviewer and unclear. name the review behind each choice. if none need attention, say so. leave github unchanged.

tuesdays at 10:00 · a review queue grouped by who needs to act

prepare release reading

every thursday at 3, read commits in amberquay/widget since monday. draft a release outline here with fixes and additions separate. flag changes whose effect on customers is unclear. if no commits match, say so. never create a release or tag.

thursdays at 15:00 · an unpublished release outline

what it asks you first

let the bot read the queue before you let it run the queue. comments count as sends and ask for allow or deny by default. a daily amount permits some sends on its own.

careful with Full access: a bot there with no sending rule can send up to 25 a day without asking. give it Ask every time.

labels, assignments, closures, merges and submitted reviews are other app changes. they don't wait for a send card. keep review bots read only; for writes, put 'ask me before you change anything' in the routine.

what it cannot do

  • keep merge and label tools outside a reading job. read only blocks merges, labels and assignments before they reach github.
  • give overnight triage an awake host. local work stops during sleep or when dusk closes; dusk cloud works with your machine off.
  • use the diff summary to decide what needs testing. these routines gather evidence; they do not run code or reproduce the bug.

give every report a repo boundary

paste the full repo name so the right queue gets attention. your github account may reach several projects. name the exact one in each routine.

explain what the labels mean before allowing label changes. if a report lacks reproduction steps, ask for them before calling the bug diagnosed.

the issue triage routine turns that into a recurring report.

let each source answer its own question

keep priority where the team plans the work. if that's linear, use linear for priority and github for issue and code context. a code comment shouldn't quietly rewrite the release plan.

a slack digest can add discussion. have the bot name the source behind each suggestion.

when sources disagree, put both in the report so the team can settle it.

questions

can i connect claude to github without building my own bot?

yes, connect github and pick the bot’s ai. those choices are separate. changing ai keeps that bot’s chats and memory.

can it close issues without asking me?

write access can permit closure without a sending card. stay read only for advice, or tell the routine to ask before any change.

where does my issue triage bot run when my laptop is closed?

local triage stops during sleep or when dusk closes. dusk cloud gives the routine an always-on machine.

free on your own computer, with every feature. no account, no card.
