turn your bug notes into a github issue with ai

a useful bug report saves the next person a round of questions. give your bot the repository and what you saw.

by the Metal team · checked 12 november 2026 · how we made this

it can file an issue with a title, body, labels and assignees. the repository must allow issues. creation is a write, so say "show me before you file it" when you want a review.

create an issue, in plain words

give the developer enough to start, without a follow-up interview. the bot needs the repository owner, name and issue title. add what happened, what you expected and the steps you actually tried. leave unknown details as questions.

labels, assignees and milestones are optional. github can quietly skip extras your account cannot set. open the finished issue to see which ones stuck.

a routine to copy

paste this into a chat with your bot

every friday at 4, read bug notes added this week to the booking-desk bug reports folder. use only notes marked ready for copperfinch/booking-desk.

- prepare a title, observed result, expected result and reproduction steps from each note
- search the repository for matching reports
- show any matches and proposed issues here

ask me before you change anything. create only the issues i confirm. don't invent steps or assign anyone. if a matching report exists, ask what to do. skip notes that already link to a filed issue.
when
fridays at 16:00
needs
access to the bug reports folder; github read and write for issue search and creation in copperfinch/booking-desk

what comes back looks like this (an example)

issue proposal: booking confirmation loses the room name
repository: copperfinch/booking-desk

renata's note: choose a room, save a booking, reopen the confirmation.
expected: the selected room name stays visible.
actual: the room field is blank.

search found no matching report. waiting before creation.

good jobs for it

  • save the demo failure. turn your customer demonstration notes into steps someone can follow.
  • make accessibility work concrete. describe the missing behaviour and exactly how you found it.
  • fix a docs gap. file the small writing change in the repository that owns it.
  • capture an agreed task. leave the deadline and owner blank unless someone chose them.

before it runs

Metal counts Create an issue as a change: it alters something in GitHub, and the sending setting does not cover it. a bot you allow only to read can never call it.

the permissions GitHub asks for to run it: public_repo, repo.

how to start

  1. name the repository exactly. connect github and give its owner and repository, not just an internal nickname.
  2. allow only needed actions. issue search and creation need read and write. read only cannot file anything.
  3. read the proposal first. tell it to wait for your confirmation before creating the issue.
  4. see what stuck. open the new issue and look for the labels, assignees and milestone you requested.

limits worth knowing

  • issues must already work there. this action cannot create a repository or turn its issues on.
  • success can hide skipped extras. github can file the issue while dropping labels, assignees or a milestone your account cannot set.
  • creation doesn't pause by itself. keep an ask-first line in the routine if you want to review it.
  • the issue starts the investigation. your evidence gives a developer somewhere to begin; filing alone neither reproduces nor fixes the bug.

a screenshot and three honest steps beat a confident paragraph about a cause nobody tried to reproduce.

try it in 2 minutes

  1. give the repository owner and name
  2. describe one actual failure and its steps
  3. ask for an issue proposal without filing
  4. look for an existing report before confirming

quick checklist

  • the repository has issues enabled
  • the steps describe what someone really tried
  • uncertain details remain questions
  • the final issue has the extras you requested

mistakes people make

filing a polished guess

leave missing evidence as questions. tidy wording cannot replace a reproduction step.

treating a successful create as a complete setup

open the issue. labels and assignments can disappear without stopping creation.

questions

can it file an issue without assigning a developer?

yes, ownership can stay blank. only the title, repository owner and repository name are required. assignees are optional.

why did my new issue appear without its label?

github can quietly drop a label your account cannot set. creation can still succeed. open the issue and look at its labels.
