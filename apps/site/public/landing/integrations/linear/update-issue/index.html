change a linear issue without replacing the wrong details

fix the deadline while the rest of the ticket stays intact. the bot finds and reads a linear issue, then changes the date, owner, priority or description you name.

by the Metal team · checked 12 november 2026 · how we made this

labels replace the whole label list. edits skip sending approval, so put a preview-and-agree step in the job before giving it write access.

where it helps

  • correct a delivery date after its owner confirms the new day
  • replace an old description with agreed steps to reproduce the problem
  • hand an issue to a new owner after matching the person to your team
  • set an agreed priority without touching the project or labels

the short version

name the ticket and the exact field to change. the bot finds the existing issue and reads it before editing. new owners and states need lookups in your workspace and that issue's team.

  • labels replace the full list; they do not append
  • a team move with state, project or cycle changes takes two stages
  • a failed second stage can leave the team changed; inspect before retrying

step by step

  1. connect linear and give the corrections bot read and write.
  2. allow issue and field lookups plus issue updates. leave unrelated tracker changes out.
  3. try one date correction. ask for the old and new date together, then agree to the edit.
  4. schedule the weekday overdue review once the saved date is right. Pause stops future runs.

send this to your bot

paste this into a chat with your bot

each weekday at 4:30, find open linear issues in the ops team whose due date has passed. show me each one here with its title, owner and current due date, and ask me what the new date should be.

ask me before you change anything, change only the due dates i give you, then tell me the saved dates. never change teams, labels, owners or priority.
when
weekdays at 4:30
needs
linear with read and write; allow team issue lookup, required field lookups and issue updates

what can go wrong

  • labels replace labels. an empty list removes them all. read the existing list before changing it.
  • team details must fit. states, projects and cycles need lookups for the issue's team.
  • read the issue before retrying a failed move. the team may have changed even if the second stage failed.
  • keep the date review supervised. write access permits edits without a sending approval card. the routine above tells it to ask.

permissions and asking first

Metal counts Update issue as a change: it alters something in Linear, and the sending setting does not cover it. a bot you allow only to read can never call it.

old date beside new date. the fastest way to spot the right edit on the wrong ticket.

try it in 2 minutes

  1. connect linear with the lookup and update actions
  2. name one ticket and ask for its current due date
  3. give a new date and ask for a preview
  4. agree to that change, then open the issue and read the saved date

quick checklist

  • the title and owner match the issue you meant
  • only the intended fields appear in the proposal
  • the routine asks before it changes anything
  • the saved issue has the agreed values

mistakes people make

sending just the new label

ask the bot to keep the old labels in the replacement list.

retrying a failed team move immediately

read the issue first. the team move may already have happened.

questions

can it add a label without losing the others?

yes, if it keeps the complete list. read the current labels first, then include every label you want to retain.

does changing a date ask me first?

put the ask-first step in the instruction. sending controls do not cover date edits. read only blocks the edit entirely.

can i describe the owner or state in normal words?

yes. you name them; the bot looks them up. if a name fits several people or states, it should ask you to choose.
