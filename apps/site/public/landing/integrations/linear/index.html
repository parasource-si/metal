a linear bot that spots missing context before planning

walk into planning with the question that is holding the work up. a Metal bot reads linear issues, comments and cycles, then brings you blockers with their evidence.

by the Metal team · checked 12 november 2026 · how we made this

give it one team and read access. it can create or update issues later if you allow it. keep priorities and edits with you until you ask for that work.

what a bot can do in Linear

find the unanswered comment behind the tidy status. read the issue, its discussion and the team's cycle before deciding what needs you. these actions bring the context to your chat.

actionMetal treats it aswhat you would use it for
Search Linear issuesreadlook for existing work before suggesting a new issue
Get Linear issuereadread the full issue before assessing whether it is ready
List commentsreadfind unanswered questions in the issue discussion
Get cycles by team IDreadinspect the cycles for the team you named
List Linear statesreadlearn the team's actual workflow states
List project updatesreadcollect project updates for a planning review
Create linear issuechangecreate an agreed issue from a prepared brief
Update issuechangechange the field you asked it to change, leaving the rest alone

composio, the connection service behind Metal's apps, lists 48 Linear actions (version 20261101_00, read 12 november 20264). Metal treats 21 as reads, 2 as sends and 25 as changes.

only actions starting with a read word (get, list, search) count as reads, so a read-only bot can't call the rest. a send reaches people or moves money, like add reaction to comment, and waits for your Allow unless you set a daily amount.

connect Linear

  1. open Connected apps in the sidebar.
  2. pick Linear and sign in on Linear's own page, so your password goes to them and never to a bot.
  3. choose which bots may use it, and whether each may only read or may also change things. your bookkeeper doesn't need your Linear.
  4. ask in plain words. reading and drafting happen freely; sending asks you first.

explain what ready and blocked mean to your team.

add linear in connected apps, sign in through linear and allow your planning bot to use it. name the team and give it a few issues to define the scope.

explain your states instead of asking the bot to guess from their names.

routines to copy

make planning questions smaller. try duplicate candidates, blocked work or missing project updates. inspect the first runs before widening the job.

possible duplicate review

every monday at 10, list issues created last week for the team named in your memory notes. compare descriptions and comments with possible older matches. use word search only to find candidates, then check each candidate's actual team and project.

show matching details and differences with both issue references. mark uncertain pairs for review. don't create, merge, close or edit anything. if the team note is missing, ask instead of guessing.

mondays at 10:00 · candidate duplicate pairs with the evidence and differences to check

cycle question list

every thursday at 2, inspect the current cycle for the team named in your memory notes. read issues in the blocked states listed there.

group blockers by the decision or input requested in comments. mark unclear reasons as unclear. leave linear unchanged. say briefly when no decision needs me.

thursdays at 14:00 · decisions and missing inputs that the issue discussion actually names

project update gaps

every other tuesday at 4, read updates for the linear projects listed in your memory notes. flag projects without an update in the last two weeks. list questions the latest update leaves open. don't publish updates or edit projects. stop if the project list is missing.

alternate tuesdays at 16:00 · a project communication checklist with gaps left visible

what it asks you first

keep the planning bot read only so the review leaves your plan intact. creating issues and changing priority, owner or state are writes that can happen without asking. creating a project update works the same way.

for maintenance later, restrict the action list and write "ask me before you change anything".

comments count as sends and wait for allow unless you set a daily amount.

careful with Full access: a bot there with no sending rule can send up to 25 a day without asking. give it Ask every time.

what it cannot do

  • assign work or change priority under read-only access. an issue outline here needs no tracker writes.
  • tell you work is finished from its state name alone. ask for the description and comments too. leave unclear readiness for a person.
  • review a cycle on a sleeping laptop. local routines need dusk open and the machine awake. dusk cloud can run the review while you are away.

keep a blocker tied to its evidence

bring both tickets and the difference between them. a similar title is a lead worth reading. name the states to inspect and require an issue or comment behind each blocker.

linear's word search cannot filter by team, owner, state, project or label. the bot uses a separate team-list action for team scope. typing a team name into search only searches for those words.

if code discussion lives in github, connect it separately and bring that context into the review.

write the rule before allowing the update

keep today's priority decision with the person who owns it. name the fields the bot may maintain and where it should report missing values. a notion note can add context without setting the plan.

product managers can gather evidence before planning, then permit tracker changes once the rules are clear.

try it in 2 minutes

  1. name one team and its blocked states
  2. connect linear read only
  3. ask for blockers with supporting issue comments
  4. check one result before scheduling a cycle review

ask what decision would unblock the work, and which comment says so. that makes the planning list worth reading.

quick checklist

  • team and project scope came from the records, not search words
  • each blocker points to the request that would unblock it
  • possible duplicates include differences as well as similarities
  • reviewing bots cannot create or edit issues

mistakes people make

typing a team name and trusting every search hit

word search only matches words. check the actual team on each result.

reading a status as the whole story

look at the description and comments. a label can hide the question that matters.

questions

can i connect claude to linear without writing an mcp setup?

yes, use connected apps. choose claude or another ai for your Metal bot and connect linear there. the composio actions need no separate server setup.

can the bot just tell me what is blocked?

yes, give it read access and the team's state names. ask for the relevant issues and comments, with evidence here. word search alone cannot narrow by team or state.

will issue creation ask me first?

put the pause in your request. issue creation is a write and can happen without asking. keep a reviewing bot read only; ask for confirmation before letting a maintenance bot create anything.
