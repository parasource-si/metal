a jira assistant that explains what changed

walk into the sprint meeting knowing what changed yesterday. a jira bot reads issues, comments and history, then explains scope and status changes in your dusk chat.

by the Metal team · checked 12 november 2026 · how we made this

schedule that review with the ai you choose. start read only. you get the story behind the labels while tickets and the sprint stay where they are.

what a bot can do in Jira

get the story behind the status label. ask for the issue, comments and available history together. the bot brings back scope changes and questions with issue references, ready for the sprint or release meeting.

actionMetal treats it aswhat you would use it for
Search Issues Using JQL Enhanced (POST)readpull the sprint issues matching your project and saved jql
Get Issuereadopen the issue behind a surprising status
Get Issue Changelogsreadfind when the scope or status changed before asking the team about it
List Issue Commentsreadread the discussion behind a reopened bug
List Sprintsreadfind the sprint your board review is about
Get Project Versionsreadbring back the project versions for the release discussion
Get Transitionsreadshow which next states the issue can move to
Transition Issuechangemove an issue through the transition you agreed, with change access enabled

composio, the connection service behind Metal's apps, lists 146 Jira actions (version 20261104_00, read 12 november 20264). Metal treats 97 as reads, 2 as sends and 47 as changes.

only actions starting with a read word (get, list, search) count as reads, so a read-only bot can't call the rest. a send reaches people or moves money, like add comment, and waits for your Allow unless you set a daily amount.

connect Jira

  1. open Connected apps in the sidebar.
  2. pick Jira and sign in on Jira's own page, so your password goes to them and never to a bot.
  3. choose which bots may use it, and whether each may only read or may also change things. your bookkeeper doesn't need your Jira.
  4. ask in plain words. reading and drafting happen freely; sending asks you first.

give it the same issue set the team uses. connect jira and choose the bot that may read it. name the project, board and sprint. "our current sprint" needs that context.

have a saved jql filter for bugs or releases? use it, then compare the first returned issues with the team's queue.

routines to copy

give each review one question to answer. use the same issue selection your team uses. these routines read evidence and return questions without moving work or promising a release.

what changed in the sprint

every weekday at 4, read the jira sprint named in your job. read the issue histories for scope and status changes since the previous workday. group additions, removals and unclear history here, with issue keys. keep reading until the relevant history is complete; flag anything you cannot read. never change the sprint.

weekdays at 16:00 · a sprint note with additions, removals and gaps in the history

why bugs reopened

every wednesday at 10, search the jira bug queue using the saved jql in your job. use our reopened-status rule from your memory notes. read matching issue histories and comments. report each reopening reason given in the issue here; leave missing reasons as questions. never assign blame or edit tickets.

wednesdays at 10:00 · reopening reasons with issue references, plus questions where the history is silent

questions before the release

every thursday at 2, read issues from our saved release filter and the relevant project version. compare them with the release checklist in your memory notes. read comments when a status is unclear. return unresolved questions here. never change versions, statuses or dates.

thursdays at 14:00 · questions for the release owner, without changing the candidate

what it asks you first

read the workflow, then choose whether the bot can change it. read-only access lets it inspect transitions and propose a next step. moving issues, assigning work and creating tickets need change access.

those edits don't wait for sending approval. if you enable writes, restrict the actions and put "ask me before you change anything" in the routine.

comments count as sends and ask unless you grant a daily amount.

careful with Full access: a bot there with no sending rule can send up to 25 a day without asking. give it Ask every time.3

what it cannot do

  • move an issue with read-only access. listing available transitions is a read; applying one is a change.
  • invent why a bug reopened. comments and history provide evidence. missing explanations should remain questions.
  • declare a release ready from a filter. the routine compares issues with your checklist and brings back unresolved work.
  • review on schedule while the local machine sleeps. Metal must be open and the computer awake. dusk cloud can keep the review running.

use your team's actual workflow

teach it what reopened means on your team. give the bot your status meanings and saved jql. compare the first report with the original issue histories.

need to know whether the code shipped? follow the release evidence, which may live in github. connect that separately when the review needs it.

make the note useful for a decision

bring the release owner questions worth answering. sprint additions help a lead discuss scope. reopening reasons help pick a bug to investigate. unresolved release questions show the owner where a decision is needed.

teams using linear can use its own issue tools. product managers get more from a focused question than another summary of everything.

ask what changed since the last workday. a full project summary rarely helps the next meeting.

try it in 2 minutes

  1. connect jira with reading access
  2. name one project and your existing issue filter
  3. ask what changed in one issue since yesterday
  4. compare the answer with the issue history

before a recurring review

  • the project, board and sprint are unambiguous
  • status meanings match your team's workflow
  • the review names gaps in history
  • it returns questions rather than changing issues

mistakes people make

treating done as proof of a release

follow the code and release evidence when you need to know what shipped.

assuming reopened means the same thing everywhere

give the bot your real status rule and verify a first example.

questions

can claude help with jira without changing tickets?

yes. a Metal bot can use the search and read actions with jira read only. these three routines return findings in chat.

will it ask before changing an issue status?

put that instruction in the routine if you enable transitions. status changes can run without asking. stay read only while you try the reviews.

what should i give a jira ai agent first?

one project, one issue selection, one question. your existing jql helps. for history reviews, include the time window and actual status meanings.
