turn your shipped work into posts you approve

turn the thing you shipped into a post someone can understand. a bot drafts from release notes you cleared for public use, with the source beside each option.

by the Metal team · checked 12 november 2026 · how we made this

compare availability, wording and links before publishing. keep sending on ask every time with no daily allowance. x needs your own composio project setup; drafting here needs no social account.

the routine

put the source somewhere the routine can read again. use an approved release-notes folder, with public links and private items clearly marked. drafting needs no social connection. connect x only for posting after review.

paste this into a chat with your bot

every friday at 1pm, read release notes added this week to the approved public releases project folder. use only notes cleared for public use.

draft two possible x posts: a user-visible change and a practical use for it. if no approved change exists, skip drafting and say why.

show the source note beside each draft. flag unclear availability. use the public link in the note; never invent one. omit private roadmap work, customer names, usage numbers, testimonials and unsupported claims.

leave drafts here. don't publish, reply, message anyone or change the account. when i later request publication, use the exact reviewed wording, including my edits.
when
fridays at 13:00; reads this week's approved release files
needs
access to the approved public releases folder; optional x connection needs your own composio project key and auth setup

what comes back looks like this (an example, not a real inbox)

x draft options for the fictional product lumenettle

option a: lumenettle now lets you rename a saved view. choose a name that matches the work.
source: chloe's approved release file, rename saved views.

option b: name a saved view handover for the items you discuss with elliot. rename an existing view instead of starting again.
source: the same release file; handover is an example use.

held back: private mobile layout work.
needs review: no public release link in the file. nothing posted.

start with shipped work you can point to

announce what customers can use today. name the approved notes and the audience with access. if rollout is unclear, the bot should ask before announcing it.

keep recurring inputs in the release folder. for a one-off draft, paste the note directly. the github guide covers a separate repository connection if you want one. this routine needs no code access.

x needs a connection you configure

draft here first; connect x when you want to publish. the twitter toolkit has a create-post action but no managed sign-in. use your own composio project key and auth configuration.3 the x guide covers the connection.

set sending to ask every time, with no daily allowance. read the text and account before allow.

careful with Full access: a bot there with no sending rule can send up to 25 a day without asking. give it Ask every time.4

a draft is not a publishing strategy

give the reader a reason to care, straight from the release. open the public link and cut benefits the note cannot support. drafts tell you neither reach nor sales.

use the newsletter routine when a release needs a longer explanation. write the social post for its own reader and revisit old drafts when the feature changes.

the guard rails

  • use public notes only. exclude private roadmap work and anything not cleared for release.
  • keep each post behind review. select ask every time and leave daily allowance off.
  • choose the final destination. read the account and exact text before allow.
  • cut claims without evidence. remove invented benefits, customer names and adoption numbers.

try it in 2 minutes

  1. attach one approved release note
  2. ask for a change post and a practical-use post
  3. compare every claim and link with the note
  4. edit the draft and publish it yourself

if nothing shipped, skip the post. a quiet friday beats announcing work customers cannot use.

mistakes people make

using a closed issue as release proof

read rollout and audience in the approved release note first.

leaving the routine's input in old chat messages

keep approved notes in the named project folder so each run has a clear source.

adding benefits the release note never claimed

describe the actual change. ask before turning a possible benefit into a promise.

quick checklist

  • the feature is available to the named audience
  • every claim traces to an approved note
  • the public link opens the right release
  • the reviewed account and wording match the post

questions

can an ai agent post on social media without me?

it can if you grant that freedom. this routine leaves drafts here. for later publication, keep ask every time and review the exact wording before allow. the full-access sending rule above matters here too.4

does x connect with the normal managed sign-in?

no, x needs your own setup. use your composio project key and auth configuration.3

can i use it just to draft posts?

yes, no x connection needed. give approved notes, review the drafts here and publish through your usual social app.
