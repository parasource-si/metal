an ai assistant for product managers with scattered context

get the blocker before standup becomes a round of guesses. a product bot reads linear or jira issues and the slack discussion behind them.

by the Metal team · checked 12 november 2026 · how we made this

name one project and a few channels. it brings decisions that need you, with links you can open. start read only and keep priorities, estimates and customer promises with your team.

from morning blockers to a release note

whenwhat a bot does
before standupbring the actual blocker. read unresolved project issues and pull explicit blockers from their comments.
after customer feedbackseparate problem from solution. find related tickets without rewriting what the customer asked for.
before planningfind the missing brief. read a small issue set for acceptance criteria; leave estimates alone.
after shippingdraft from confirmed releases. name unresolved rollout questions instead of hiding them.
end of daycatch the decision you missed. read a slack digest for the channels you chose.

the routines

the standup evidence list

every weekday at 8:45, read open issues and comments in the linear project i named. list explicit blockers, unanswered questions and decisions that need me.

link each item to its issue and name who last raised it. don't infer that quiet work is blocked. change no status, priority, owner or estimate. say when no decision needs me.

one tracker is enough. use linear, or name one jira project instead.

the feedback trail

every tuesday at 2, read the last week's messages in my chosen slack feedback channel. group requests by the problem people describe.

search the named jira project for related issues. pair message and issue references. distinguish possible matches from confirmed ones. suggest discovery questions, but create nothing.

read the evidence, leave the tickets. jira search and slack history need no ticket-writing access.

the release update draft

every friday at noon, read this week's release issues and comments in the connected tracker project. use its release label to choose the scope.

draft a short update here: confirmed shipped work, open rollout questions and facts i need to verify. use release evidence beyond a closed ticket to confirm customer availability. don't post the update or edit the roadmap.

name the release boundary. keep unrelated teams out by choosing the project and release label.

choose one home for each fact

know which source owns the delivery date. name the tracker for status and the slack channels for discussion. a copied ticket adds no new evidence. put project boundaries in the routine instead of relying on a broad keyword.

linear and jira both support issue and comment reads. connect the tracker your team uses. fewer sources make missing or contradictory details easier to spot.

ask for the disagreement, not a smoother story

keep the uncomfortable contradiction in the brief. if a ticket and later message disagree, ask for both links and dates. leave the conclusion open until someone resolves it.

repeated requests can guide discovery. they don't automatically outrank reliability, accessibility or a commitment your team already made. people still own that trade-off.

read first, publish deliberately

get the brief without moving the roadmap. set tracker and slack access to read only. the bot can report here without changing tickets or announcing dates.

for edits later, require "ask me before you change anything". ordinary tracker changes can happen without a sending prompt.7

company work needs a work license. see billing.

ask for the disagreement and its dates. a clean story is less useful than the conflict you can resolve.

try it in 2 minutes

  1. pick one project and its source tracker
  2. connect it and slack read only
  3. ask for blockers with the comments that name them
  4. open a few source links before scheduling standup

quick checklist

  • delivery status has one named source
  • every blocker points to evidence
  • conflicting dates remain visible
  • a closed ticket is not the only release proof

mistakes people make

calling quiet work blocked

require an explicit blocker from the issue or discussion.

turning repeated requests straight into priority

use them as discovery evidence. compare them with existing commitments before changing the plan.

questions

what would a product manager actually schedule an ai to do?

collect the evidence you keep chasing. try standup blockers, feedback linked to issues or a release update draft. start with a handful of links you can compare with the brief.

can it work with jira instead of linear?

yes, name one jira project. a read-only bot can search issues and read comments. you do not need to connect linear too.

will it update tickets while summarising them?

read-only access blocks that. keep it while trying the pack. if you later allow writes, name the fields and require review before changes.
